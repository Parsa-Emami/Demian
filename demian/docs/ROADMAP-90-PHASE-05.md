# Roadmap 90+ — Phase 05: verified phone identity and anti-multi-account

Stacked on Phase 04. No host access, external SMS sent, secrets, financial flags or provider credentials changed.

## Trust model
- A contact address is not proof of ownership. Players may still play practice or earn technical server-verified scores; new live weekly financial allocations require a unique SMS-verified phone. A phone is a proxy for one customer, NOT one natural person: SIM sharing, recycled numbers, multiple SIMs, collusion and stolen devices remain possible.
- Server normalizes Iranian/local/international digits to E.164 and encrypts verified phones. A separate owner-supplied stable HMAC key protects unique phone lookup, OTP digests, device digests and weekly scoped claims. No OTP, full phone, recovery secret, device ID or gateway token in public/admin review logs. Do not rotate the identity key without an approved migration/reconciliation; losing it prevents recovery/issuance.
- OTP is random 6 digits, purpose/account/current session or recovery capability bound, 5 minute expiry, 5 committed attempts, atomic cooldown 60 seconds, account 3/hour and per phone 5/day; transport uses a pinned operator-configured HTTPS adapter URL with bearer authentication, no redirect/retry. JSON request {to,code,request_id,template,expires_in}; only 2xx JSON {accepted:true} enables a challenge. Integrate and validate a real vendor adapter and consent before enabling; no mock/test bypass in production. SMS provider delivery is not guaranteed by successful acceptance.
- Recovery for verified accounts additionally demands fresh OTP on the already-verified phone. Rotate bearer and consume both recovery grants only after both proofs. Enrollment invalidates earlier recovery grants. No self-service verified phone change or SMS-only login; lost/recycled numbers require a reviewed assisted recovery procedure, not operator bypass of proof.
- Random optional installation UUID in device-local storage. No private browsing detection, hardware or browser fingerprinting. HMAC by calendar month. Three associated verified accounts produce review-only evidence; duplicate verified phone and shared Wi-Fi likewise never independently justify a hold. Existing contact/registration deduplication remains unchanged. Clearing cookies or Incognito does not bypass phone uniqueness. Existing contact-registration uniqueness can still require an alternate contact/recovery for an unverified squatted phone; ownership verification is independent.
- New financial campaigns freeze identity policy inside terms digest. Count only verified phone accounts toward the 20 minimum; maintain original technical ranks. Store week-scoped HMAC claim per sealed winner with SQL UNIQUE(period,identity) and unique winner. Claim creation and seal atomic. Check claim and validity before minting any new payout. Erasure cascades encrypted phone, challenges and device metadata; award claim remains for 28 days or open coupon liability, blocks immediate deletion/re-registration within prior award validity (14 days); former account history anonymized. Hourly/phone counters expire; challenges and device observations pruned even with SMS off. Existing weekly history remains authoritative; unsealed legacy funded campaigns need reconciliation before issuance. Gifts are separately gated; this policy covers weekly financial awards.
- Privacy export includes own verified phone and date only; legal source bumped to 2026-11-20-v3, pending review. Admin anti-cheat review uses current existing permissions, no raw identifiers beyond existing internal account ID. Financial activation preflight requires configured SMS identity when weekly issue/campaign flags on. No actual SMS, device, or customer UAT.

## Verification
Dedicated SQLite/MySQL feature coverage for normalized uniqueness, cross-account OTP, attempts, expiry, recovery, fail-closed send, erase, financial participation, rank preservation and re-registration claims. Gateway HTTP faked. Added review-only shared-device and retention tests; audit checks scoped claims without displaying them. Existing regression tests remain. Acceptance requires real provider, ownership/lost-number policy, legal review and physical-cafe pilot before host activation.
